# MVP-scope: статус реализации

**Дата документа:** 2026-05-28
**Источник:** анализ кодовой базы `KotaTask-main/android/`

## Что реализовано (готово к использованию)

### Базовый CRUD задач
- ✅ Создание задачи (`AddTaskFragment` в режиме create) с обязательным title,
  необязательными дедлайном/началом диапазона/длительностью/целью/важностью.
- ✅ Редактирование задачи (`AddTaskFragment.forEdit(id)`).
- ✅ Удаление задачи (с диалогом подтверждения).
- ✅ Изменение статуса: "В Сегодня", "В Стек", "Выполнить" (→ Архив).
- ✅ Архив с timestamp выполнения и массовым удалением.

### Алгоритмический приоритет
- ✅ `PriorityCalculator` с 4 факторами и пользовательскими весами.
- ✅ Скор отображается badge'м на карточке задачи (за исключением архивных).
- ✅ 7 режимов сортировки (`SortMode`): priority, importance, deadline, age,
  alphabetical, by_project, duration.
- ✅ Overload-механика: цветовая индикация дневной нагрузки + boost коротких задач.

### Три оси категоризации
- ✅ CRUD проектов / локаций / типов задач (`addProject`/`renameProject`/`deleteProject`
  и аналоги для остальных).
- ✅ Привязка задачи к одной категории каждой оси.
- ✅ Папки (`FoldersFragment`) — навигация по категориям + системная "Без X".
- ✅ Фильтрация в Стеке по локации и типу.
- ✅ Quick-add новой категории прямо из формы создания задачи.

### Календарь
- ✅ Месячная сетка с donut-индикаторами загрузки дня.
- ✅ Переключение режима "диапазон" / "точка".
- ✅ Тап по дню показывает задачи на эту дату.
- ✅ Навигация между месяцами.

### Уведомления
- ✅ Ежедневное утреннее уведомление в заданное `HH:MM`.
- ✅ `BootReceiver` для перепланирования после ребута.
- ✅ Android 13+ runtime-permission запрашивается при первом запуске.

### Онбординг и настройки
- ✅ 7-шаговый онбординг при первом запуске.
- ✅ Дублирование всех настроек в `SettingsFragment`.
- ✅ Динамические шаги (если выключен smart-sort — пропускается шаг коэффициентов).
- ✅ 4 уровня assistance (minimal / standard / advanced / custom).

### UX / визуал
- ✅ Light / dark / system тема.
- ✅ Поиск по задачам в Стеке.
- ✅ Material 3 компоненты.
- ✅ Анимации перехода между фрагментами.
- ✅ Русская плюрализация для счётчиков задач.
- ✅ Контактные ссылки в Settings (email, telegram-канал, форма предложений).

### DevOps

## Что выглядит незаконченным или подозрительным

### 🟡 Поле `assignee` — мёртвый код в схеме
В `Task` есть поле `assignee: String`, но в UI оно вырезано (см. коммит
`3c119bf fix: remove assignee field`). Префера `KEY_FIELD_ASSIGNEE`
не существует (только `KEY_FIELD_DURATION`, `KEY_FIELD_PURPOSE`, `KEY_FIELD_PROJECT`).
В комментарии `AddTaskFragment.applyFieldVisibility()`:
> Поле «Ответственный» (KEY_FIELD_ASSIGNEE) пока не реализовано в разметке —
> флаг сохраняется в prefs, но визуально ни на что не влияет.

**Решение:** либо удалить из схемы (миграция v3→v4), либо восстановить в UI.

### 🟡 Поле `parent` — двойной механизм проектов
После v2 миграции основной механизм проектов — `projectId` (FK на таблицу `projects`).
Но `parent` (legacy free-text) **сохраняется в схеме** и используется в:
- `SortMode.BY_PROJECT` — сортирует по `parent`, а не по `projectId`.
- `TaskViewModel.getProjectSuggestions()` — собирает уникальные значения `parent`.
- `TaskAdapter` — показывает `parent` в карточке.

При этом `AddTaskFragment.submitTask()` всегда передаёт `parent = ""` для новых задач.
То есть **новые задачи никогда не заполнят `parent`**, и сортировка `BY_PROJECT`
для них вернёт только задачи без группировки.

**Решение:** либо переписать `BY_PROJECT` через `projectId`+`projects.name`, либо
дублировать запись (при выборе проекта писать и `projectId`, и `parent`).

### 🟡 Удаление проекта/локации/типа не очищает ссылки
`vm.deleteProject(id)` удаляет строку из таблицы `projects`, но задачи с этим
`projectId` остаются — у них в поле висит "битый" id, который не резолвится в имя.
В UI это не ошибка (просто покажется hint "Проект не выбран"), но данные дрейфуют.

В Room это решается через `@ForeignKey(onDelete = SET_NULL)`, но FK в проекте нет.

**Решение:** либо добавить FK, либо в репозитории при `delete()` обновлять все задачи
с этим id, ставя `projectId = null`.

### 🟡 INTERNET permission заявлен, но не используется
В `AndroidManifest.xml` есть `<uses-permission android:name="android.permission.INTERNET"/>`,
но в зависимостях нет HTTP-клиента (Retrofit/OkHttp/Ktor) и в коде нет вызовов сети.

**Решение:** удалить permission, если не планируется сеть; либо документировать
планируемое использование.

### 🟡 Релизная сборка без минификации
`buildTypes.release.minifyEnabled false`. R8/ProGuard правила декларированы,
но не применяются. Это значит:
- APK не уменьшается.
- Код не обфусцируется.
- Нет проверки, что миграции и DAO не дропаются proguard'ом.

**Решение:** включить `minifyEnabled true` в release и протестировать.

### 🟡 Нет тестов
Папок `app/src/test/` и `app/src/androidTest/` нет (только `app/src/main/`).
Это значит:
- `PriorityCalculator` (чистая функция, идеально тестируемая) не покрыт.
- Миграции Room не тестируются — что особенно опасно с учётом ADR-001.
- Регрессии при добавлении новых фич ловятся только глазами.

### 🟡 `exportSchema = false`
В `@Database` стоит `exportSchema = false`. Это значит:
- Schema-файлы в `app/schemas/` не генерируются.
- Невозможно автоматически валидировать миграции через `MigrationTestHelper`.

**Решение:** включить `exportSchema = true` и закоммитить `app/schemas/*.json`.

### 🟡 Несоответствие APK naming convention
- В `app/build.gradle` `afterEvaluate` копирует APK как `KotaTask_${yyyyMMdd_HHmm}.apk`.
- В auto-memory зафиксирована конвенция: `KotaTask-v{X.Y}-{feature-slug}-debug.apk`.

То есть Gradle-скрипт **не реализует** заявленную конвенцию — имена приходится
переименовывать руками.

### 🟡 Поле `purpose` есть, но не отображается на карточке
В `Task` есть `purpose: String` ("цель задачи"), оно сохраняется при создании и
участвует в поиске (`title.contains || purpose.contains`). Но в `TaskAdapter`
оно нигде не показывается. Это либо забытая фича, либо сознательно скрыто
до hover/tap.

### 🟡 Версия в build.gradle отстала
`versionName "1.0"` / `versionCode 1`, но в `Builds/` есть APK до `v2.4`. Значит,
до коммита `2761f0c Merge remote changes` версия в gradle не обновлялась
руками — релиз идёт по timestamp APK, а не по versionCode.

**Решение:** автоматизировать bump версии через Gradle-таск или хук.

## Общая оценка готовности

| Область | Готовность |
|---|---|
| CRUD задач | 95% (мелкие баги в каскадных удалениях) |
| Алгоритм приоритета | 90% (нет тестов) |
| Категоризация | 80% (есть legacy `parent` рядом с новым `projectId`) |
| Календарь | 90% |
| Уведомления | 85% (нет обработки edge-case с долго выключенным телефоном) |
| Онбординг | 95% |
| Тёмная тема | 100% |
| Тестовое покрытие | **0%** |
| Релизная конфигурация | 60% (нет minify, нет export schema) |

**Готов ли продукт к публичному релизу?** В техническом смысле — почти.
Главные риски: миграции Room без тестов + 0% покрытия + неработающая минификация.
