# ADR-002 — Линейная взвешенная формула приоритета с настраиваемыми коэффициентами

- **Статус:** Принято (видно в коде)
- **Дата:** 2026-05-28
- **Контекст модуля:** `util/PriorityCalculator.kt`, `viewmodel/TaskViewModel.kt`

## Контекст

Сортировка задач — главная ценность приложения. Альтернативы:
1. Жёсткая сортировка по дедлайну (как в большинстве todo).
2. Жёсткий приоритет (Высокий/Средний/Низкий вручную).
3. Алгоритм Eisenhower-матрицы (важное×срочное).
4. Машинное обучение / LLM ранжирование.
5. **Взвешенная сумма нескольких факторов с пользовательскими весами.**

## Решение

Выбран вариант 5 — **линейная свёртка 4 факторов**:
```
score = w_deadline · dl  +  w_importance · imp  +  w_duration · dur  +  w_age · age
```

Где каждый фактор нормирован в `[0, 1]`:
- `dl` — пятиступенчатая функция (просрочено / сегодня / ≤3д / ≤7д / дальше).
- `imp` — три ступени (Высокая=1.0 / Средняя=0.6 / Низкая=0.2).
- `dur` — пять ступеней по минутам (≤15 → 1.0 / ≤30 / ≤60 / ≤120 / >120).
- `age` — линейный рост 0 → 1 за первые 5 дней с момента создания.

**Веса по умолчанию:** `0.45 / 0.35 / 0.10 / 0.10` (сумма 1.0, но не нормируются жёстко).
Пользователь меняет их слайдерами в онбординге и в [[../product/overview#7-онбординг-с-feature-flags]].

**Перегрузка дня (overload):** дополнительный механизм. Если суммарная длительность
задач в "Сегодня" > половины настроенного лимита (по умолчанию 180 мин), у коротких
задач включается `loadDurationBoost` (по умолчанию +0.2 к `durationScore`, capped at 1.0).
Идея: при перегрузе разумнее закрыть мелочи, чем пытаться втиснуть ещё крупное.

## Альтернативы, которые отвергнуты (вывод из кода)

- **Жёсткие приоритеты вручную** — отвергнуто; есть только три уровня важности,
  и они — лишь один из четырёх факторов.
- **ML / LLM** — отвергнуто; всё локально, без интернета (`INTERNET` permission
  заявлен, но в коде не используется).
- **Eisenhower 2×2** — отвергнуто; важность + дедлайн действительно есть, но
  добавляются ещё длительность и возраст, и это уже не 2×2 матрица.

## Последствия

**Плюсы:**
- Полная прозрачность: пользователь видит скор (badge на карточке) и понимает,
  почему задача наверху.
- Настраиваемость: можно сделать чисто-дедлайновое или чисто-важностное приложение.
- Чистая функция: `PriorityCalculator` не имеет состояния, идеально тестируется.

**Минусы / риски:**
- Сумма весов **не нормируется** к 1 — пользователь может выкрутить все в 0 или все в 100,
  и поведение будет странным (но не упадёт).
- Ступенчатые функции дают "обрывы" — задача с дедлайном через 4 дня имеет тот же скор,
  что и через 7. Может быть неинтуитивно.
- Нет тестов на формулу — см. [[../status/mvp-scope]].
