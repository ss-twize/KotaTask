# ADR-001 — Явные Room-миграции без `fallbackToDestructiveMigration`

- **Статус:** Принято (видно в коде)
- **Дата:** 2026-05-28
- **Контекст модуля:** `data/AppDatabase.kt`

## Контекст

KotaTask — task-менеджер. Данные пользователя (задачи) — единственная ценность, которую
приложение хранит. Их потеря = катастрофа доверия. Room по умолчанию умеет работать
в двух режимах при изменении схемы:
1. `fallbackToDestructiveMigration()` — БД сносится при несовпадении версии.
2. Явные `Migration(N-1, N)` — ALTER TABLE-патчи сохраняют данные.

## Решение

В `AppDatabase.getInstance()` **намеренно** не вызывается `fallbackToDestructiveMigration()`.
Вместо этого подключаются явные миграции:
- `MIGRATION_1_2` — добавляет 3 nullable колонки (`projectId`, `locationId`, `taskTypeId`)
  и три новые таблицы (`projects`, `locations`, `task_types`).
- `MIGRATION_2_3` — добавляет `deadlineStart TEXT NOT NULL DEFAULT ''`.

Авторский комментарий в коде:
> Намеренно НЕ используем `fallbackToDestructiveMigration`: потеря всех задач при
> ошибке миграции — худший возможный сценарий для таск-менеджера. Любая будущая
> версия схемы ОБЯЗАНА иметь явную `Migration(N-1, N)`, иначе приложение упадёт
> при старте, а данные останутся целыми.

## Последствия

**Плюсы:**
- Данные пользователя сохраняются между версиями.
- Каждая миграция документирует, что именно изменилось в схеме.
- Failure-mode — crash на старте, что **видно** разработчику и QA, в отличие от
  тихой потери данных.

**Минусы / обязательства:**
- Каждый PR, меняющий `@Entity`, обязан добавить новую `Migration`.
- Нет `exportSchema = true`, поэтому Room не валидирует миграции при сборке.
  Тестов на миграции тоже нет (см. [[../status/mvp-scope]]).
- Если миграция написана криво (например, NOT NULL без DEFAULT) — crash на старте
  на всех устройствах с предыдущей версией.
