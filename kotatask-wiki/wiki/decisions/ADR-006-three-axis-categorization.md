# ADR-006 — Три независимые оси категоризации (Project / Location / TaskType)

- **Статус:** Принято (видно в коде)
- **Дата:** 2026-05-28
- **Контекст модуля:** `data/Project.kt`, `data/Location.kt`, `data/TaskType.kt`, миграция v1→v2

## Контекст

У задачи нужна была "группировка". Варианты:
1. Одно поле `category` / `parent` со свободным текстом (это и было в v1, поле `parent`).
2. **Три ортогональные оси: проект, локация, тип действия.**
3. Теги (many-to-many).
4. Древовидные категории / папки.

## Решение

Выбран вариант 2. В миграции v1→v2 добавлены три nullable foreign-key поля в `tasks`
и три отдельные таблицы:
- `projects` — крупная смысловая группа (`"Сайт для клиента"`, `"Личный бренд"`).
- `locations` — место/контекст выполнения (`"Дом"`, `"Зал"`, `"Компьютер"`).
- `task_types` — характер действия (`"Звонок"`, `"Создание"`, `"Тренировка"`).

В UI:
- Вкладка "Папки" показывает три секции, каждая со своим списком + системная папка "Без X".
- Форма создания задачи имеет три row'а — каждый открывает picker со списком +
  "Очистить" + "+ Добавить новый".
- В Стеке есть spinner-фильтры по локации и типу (с sentinel-значениями
  `FILTER_ANY` / `FILTER_NONE`).

Каждая ось включается/выключается отдельно (`KEY_FEATURE_PROJECTS`, `KEY_FEATURE_LOCATIONS`,
`KEY_FEATURE_TASK_TYPES`) — пользователь может оставить только проекты или только локации.

## Обоснование (вывод из кода и комментариев)

Из комментариев в entity-классах видно, что задумано три **разных смысловых измерения**,
которые могут пересекаться: задача "позвонить врачу" одновременно относится к
проекту "Здоровье", локации "Телефон", типу "Звонок". Одного поля `category` для
этого недостаточно — пришлось бы выбирать, и набор был бы плоским.

## Альтернативы, отвергнутые

- **Теги (many-to-many)** — потребовали бы join-таблицу `task_tags`, UI с автодополнением,
  фильтрацию по комбинациям. Сложнее и в БД, и в UX.
- **Деревья папок** — пользователю придётся думать об иерархии, что часто
  блокирует на первом шаге.

## Последствия

**Плюсы:**
- Любая комбинация любых трёх осей — фильтрация комбинируется через
  `applyCategoryFilters(tasks, p, l, t)`.
- Каждая ось переключаема — приложение масштабируется от минимального
  ("только проекты") до полного ("всё включено").

**Минусы / риски:**
- **Нет внешних ключей в Room**. При удалении проекта `projectId` у задач остаётся —
  они становятся "битыми" (id указывает на несуществующий проект). UI это
  не показывает явно, в `refreshCategoryLabels()` просто `firstOrNull` вернёт null
  и подставится hint. Данные не падают, но дрейфуют. Это — баг или сознательное
  решение оставить tombstones — в коде не задокументировано. См. [[../status/mvp-scope]].
- Поле `parent` (legacy текстовое "название проекта") **не удалено** — используется
  в `SortMode.BY_PROJECT` и в `getProjectSuggestions()`. То есть фактически
  существует два механизма группировки: новый `projectId` и старый `parent`,
  и они **не синхронизируются** между собой.
