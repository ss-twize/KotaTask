## 1. Что делает приложение

KotaTask — нативный Android-таск-менеджер с **алгоритмическим приоритизатором**.
Отличие от обычного todo-листа: приложение считает численный скор каждой задачи по
четырём факторам (дедлайн, важность, длительность, возраст) и сортирует список так,
чтобы сверху оказалась задача, которую рациональнее сделать прямо сейчас.
Веса факторов задаёт сам пользователь слайдерами.

Второй смысловой слой — **настраиваемость объёма интерфейса**. Онбординг из 7 шагов
позволяет отключить вкладки, поля формы и целые функции, поэтому одно и то же
приложение может работать и как минималистичный список, и как развёрнутая система
с тремя осями категоризации, календарём и отложенным планированием.

**Ключевые свойства:**

- Данные полностью локальные (Room/SQLite), сети нет, аккаунтов нет.
- Один пользователь — одно устройство.
- Интерфейс только на русском языке (локаль зашита в коде).
- Монетизация на текущем этапе — добровольное пожертвование (кнопка CloudTips).

**Чего в приложении нет:** синхронизации, шеринга, вложений, повторяющихся задач,
напоминаний на конкретную задачу (только общий утренний дайджест), виджетов,
аналитики, crash-репортинга, автотестов.

## 5. Архитектура

### Слои

```
Fragment / Activity
      │  by activityViewModels()      ← одна общая VM на всё приложение
      ▼
TaskViewModel (AndroidViewModel)
      │  поля класса, создаются в конструкторе
      ▼
TaskRepository · ProjectRepository · LocationRepository · TaskTypeRepository
      │  withContext(Dispatchers.IO)
      ▼
TaskDao · ProjectDao · LocationDao · TaskTypeDao   (Room, KSP-генерация)
      ▼
SQLite: mark_db
```

Параллельно этому идёт вторая, независимая ветка состояния:

```
Fragment / Activity / Worker ──► SharedPreferences "mark_prefs"
```

Настройки **не проходят** через ViewModel и не реактивны: каждый экран читает
`SharedPreferences` напрямую там, где нужно. Изменение флага вкладок применяется
через ручной вызов `MainActivity.applyFeatureFlagsToNav()`.

### Ключевые архитектурные решения

**Единая ViewModel.** `TaskViewModel` держит все четыре репозитория и шарится
между всеми фрагментами через `by activityViewModels()`. Отдельных VM на экран нет.

**Single source of truth через LiveData.** `TaskDao.getAllTasks()` возвращает
`LiveData<List<Task>>`; Room сам уведомляет подписчиков при любом изменении таблицы.
Каждый фрагмент подписывается на `vm.allTasks` и самостоятельно строит свой срез —
фильтрует по статусу, категориям и поисковому запросу, затем сортирует.
Инкрементальных запросов нет: любое изменение перечитывает весь список.

**Ручная навигация.** Navigation Component не используется. Вкладки переключаются
через `FragmentManager.replace()` без back stack; модальные экраны (создание задачи,
архив, папки, задачи категории) открываются через `openModalFragment()` с
`addToBackStack("modal_…")`. Кнопка «назад» возвращает на выбранную вкладку.

**Ручной DI.** `AppDatabase.getInstance()` — синглтон с `@Volatile` + `synchronized`;
репозитории создаются прямо в конструкторе `TaskViewModel`.

**Канал ошибок.** Все мутирующие операции VM обёрнуты в `launchTracked(msg) { … }`:
исключение из корутины публикуется в `_errors: MutableLiveData<String?>`.
`MainActivity` подписывается, показывает `Toast` и немедленно вызывает
`consumeError()` — иначе `LiveData` при пересоздании активности отдала бы последнее
значение повторно и Toast появился бы снова.

```kotlin
private fun launchTracked(errorMessage: String, block: suspend () -> Unit) {
    viewModelScope.launch {
        try { block() } catch (e: Exception) {
            _errors.postValue("$errorMessage: ${e.message ?: e.javaClass.simpleName}")
        }
    }
}
```

## 6. Модель данных

База `mark_db`, четыре таблицы, **схема версии 4**.
`exportSchema = false` — JSON-схемы в репозиторий не пишутся.
Режим журнала — `JournalMode.TRUNCATE`: WAL-файл не создаётся, каждая запись
фиксируется прямо в `mark_db`, чтобы Auto Backup всегда видел актуальное состояние.

### Таблица `tasks`

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `id` | TEXT PK | — | UUID, генерируется в `TaskViewModel.addTask()` |
| `title` | TEXT | — | Название. Единственное обязательное поле на всех уровнях помощи |
| `deadline` | TEXT | `""` | Конец дедлайна, ISO `YYYY-MM-DD` |
| `deadlineStart` | TEXT | `""` | Начало диапазона. Пусто → отсчёт от даты создания |
| `parent` | TEXT | `""` | **Legacy**: свободный текст «название проекта». Новые задачи всегда пишут `""` |
| `purpose` | TEXT | `""` | Цель / описание. Участвует в поиске по стеку |
| `duration` | INTEGER | `30` | Минуты. Валидация в форме: 1…600 |
| `importance` | TEXT | `"Средняя"` | `Высокая` / `Средняя` / `Низкая` |
| `status` | TEXT | `"Стек"` | `Стек` / `Сегодня` / `Архив` |
| `assignee` | TEXT | `""` | **Мёртвое поле**: в UI отсутствует, всегда пусто |
| `created` | INTEGER | `now()` | Unix-мс создания. Вход в расчёт возраста |
| `completed` | INTEGER | `0` | Unix-мс выполнения. Заполняется при переходе в архив |
| `projectId` | TEXT NULL | `null` | Ось 1 — проект |
| `locationId` | TEXT NULL | `null` | Ось 2 — локация |
| `taskTypeId` | TEXT NULL | `null` | Ось 3 — тип задачи |
| `deferredDate` | TEXT | `""` | ISO-дата автопереноса в «Сегодня». Пусто → не отложена |

### Таблицы категорий

Три независимые оси, каждая — своя таблица. Это не enum: списки значений создаёт
сам пользователь.

| Таблица | Поля | Смысл |
|---|---|---|
| `projects` | `id` PK, `name`, `color` NULL, `created`, `updated` | Крупная смысловая группа: «Сайт для клиента» |
| `locations` | `id` PK, `name`, `created`, `updated` | Место выполнения: «Дом», «Зал», «Компьютер» |
| `task_types` | `id` PK, `name`, `created`, `updated` | Характер действия: «Звонок», «Создание» |

Задача может одновременно принадлежать одному проекту, одной локации и одному типу —
оси не конкурируют. Поле `color` у проектов объявлено, но в UI не используется.

### Связи и целостность

**Внешних ключей нет.** Целостность поддерживается вручную: у каждого
DAO категорий есть запрос `unlinkFromTasks(id)`, и репозиторий вызывает его
перед удалением:

```kotlin
suspend fun delete(id: String) = withContext(Dispatchers.IO) {
    dao.unlinkFromTasks(id)   // UPDATE tasks SET projectId = NULL WHERE projectId = :id
    dao.deleteById(id)
}
```

Это работает, пока удаление идёт только через репозиторий. Прямое удаление в обход
(например, через `seed_tasks.sh` или внешний SQLite-клиент) оставит осиротевшие ссылки.

### Миграции

`fallbackToDestructiveMigration` **не используется намеренно**: для таск-менеджера
потеря всех задач хуже краха при старте. Любая новая версия схемы обязана иметь явную
`Migration(N-1, N)`, иначе приложение упадёт, но данные останутся целы.

| Переход | Что делает |
|---|---|
| **1 → 2** | Добавляет в `tasks` три nullable-колонки (`projectId`, `locationId`, `taskTypeId`); создаёт таблицы `projects`, `locations`, `task_types`. Существующие задачи получают `NULL` во всех трёх осях |
| **2 → 3** | `ALTER TABLE tasks ADD COLUMN deadlineStart TEXT NOT NULL DEFAULT ''` — пустая строка означает «начало = дата создания» |
| **3 → 4** | `ALTER TABLE tasks ADD COLUMN deferredDate TEXT NOT NULL DEFAULT ''` — существующие задачи не отложены |

### Операции DAO, заслуживающие внимания

```sql
-- Пакетный перенос отложенных задач, чья дата наступила.
-- Лексикографическое сравнение ISO-дат корректно, поэтому строковый <= работает.
UPDATE tasks SET status = 'Сегодня', deferredDate = ''
WHERE deferredDate != '' AND deferredDate <= :today AND status = 'Стек'
```

Условие `status = 'Стек'` защищает от воскрешения задачи, которую пользователь
успел вручную выполнить или перенести, пока она была отложена.

Статусы хранятся **русскими строковыми литералами** прямо в SQL-запросах
(`'Сегодня'`, `'Архив'`, `'Стек'`). Это делает любое переименование статуса
миграцией данных, а не правкой enum.

## 7. Алгоритм приоритизации

Файл: `util/PriorityCalculator.kt`.

### Формула

```
score = w_deadline · S_deadline
      + w_importance · S_importance
      + w_duration · S_duration
      + w_age · S_age
```

Каждый частный скор нормирован в `[0, 1]`. Сумма весов **не нормализуется** —
пользователь может выставить слайдеры так, что сумма будет 0.2 или 3.0.
На порядок сортировки это не влияет (монотонное преобразование), но абсолютное
число в бейдже карточки станет несопоставимым с чужими настройками.

### Частные скоры

**Дедлайн** (`S_deadline`) — пять зон срочности:

| Условие | Значение |
|---|---|
| Поле пустое либо не распарсилось | 0.3 |
| Просрочено (дней до дедлайна < 0) | 1.0 |
| Сегодня (0 дней) | 0.9 |
| 1–3 дня | 0.7 |
| 4–7 дней | 0.5 |
| Больше 7 дней | 0.2 |

Задача без дедлайна (0.3) стоит выше далёкой задачи (0.2) — «когда-нибудь»
считается чуть более срочным, чем «точно не скоро».

**Важность** (`S_importance`): `Высокая` → 1.0, `Средняя` → 0.6, `Низкая` → 0.2,
неизвестное значение → 0.6.

**Длительность** (`S_duration`) — короткие задачи ценнее, плюс бонус при перегрузке:

| Длительность | База |
|---|---|
| ≤ 15 мин | 1.0 |
| 16–30 мин | 0.8 |
| 31–60 мин | 0.6 |
| 61–120 мин | 0.4 |
| > 120 мин | 0.2 |

```kotlin
val boostThreshold = overloadLimitMinutes.coerceAtLeast(1) / 2
val boost = if (dayLoad > boostThreshold) loadDurationBoost.coerceIn(0f, 1f) else 0f
return (base + boost).coerceAtMost(1.0f)
```

То есть когда суммарная длительность задач «Сегодня» превышает **половину**
порога перегрузки, все короткие задачи получают добавку `load_duration_boost`
(по умолчанию 0.2). Логика: при забитом дне рациональнее закрыть мелочь, чем
застрять в крупной задаче. Результат обрезается сверху единицей, поэтому задачи
≤ 15 мин бонуса фактически не получают — они уже на потолке.

**Возраст** (`S_age`) — линейный рост первые 5 дней:

```kotlin
val daysOld = (System.currentTimeMillis() - createdAt) / (1000 * 60 * 60 * 24)
return if (daysOld >= 5) 1.0f else (daysOld / 5.0f).coerceIn(0f, 1f)
```

Задача, пролежавшая 5+ дней, получает максимум — так старьё «всплывает» наверх.

| Фактор | Ключ prefs | Значение по умолчанию |
|---|---|---|
| Дедлайн | `coeff_deadline` | 0.45 |
| Важность | `coeff_importance` | 0.35 |
| Длительность | `coeff_duration` | 0.10 |
| Возраст | `coeff_age` | 0.10 |

Слайдеры в настройках и онбординге работают в целых процентах (0…100) и делятся
на 100 при сохранении, поэтому шаг веса — 0.01.

> **Внимание:** в `data class Coefficients` прописаны **другие** значения по
> умолчанию — `0.50 / 0.30 / 0.15 / 0.05`. Они никогда не применяются, потому что
> `TaskViewModel.getCoefficients()` всегда конструирует объект явно из prefs.
> Это ловушка при чтении кода, см. §15.

### Перегрузка дня

| Параметр | Ключ | Диапазон | По умолчанию |
|---|---|---|---|
| Порог перегрузки | `overload_limit_minutes` | 120…960, шаг 10 | 180 мин |
| Бонус короткой задачи | `load_duration_boost` | 0.0…1.0 | 0.2 |
| Функция включена | `feat_overload` | bool | `true` |

Светофор суммарной нагрузки одинаков на вкладках «Сегодня» и «Стек»:

- **зелёный** — нагрузка < половины порога;
- **жёлтый** — между половиной и порогом;
- **красный** — порог превышен.

При выключенном `feat_overload` расчёт приоритета получает
`overloadLimit = Int.MAX_VALUE / 2` и `boost = 0f`, то есть бонус короткой задачи
не срабатывает никогда. Светофор при этом продолжает рисоваться — он читает
`getOverloadLimitMinutes()` напрямую, минуя флаг.

## 8. Сортировка и фильтрация

### Режимы сортировки

`enum class SortMode` — семь режимов, доступны в спиннере на вкладках «Сегодня» и «Стек»:

| Режим | Подпись | Логика |
|---|---|---|
| `PRIORITY` | По приоритету | Убывание скора из `PriorityCalculator` |
| `IMPORTANCE` | Важность | Высокая → Средняя → Низкая, внутри группы по названию |
| `DEADLINE` | Дедлайн | По возрастанию даты; задачи без дедлайна уходят в конец |
| `AGE` | Возраст задачи | По возрастанию `created` (старые первыми) |
| `ALPHABETICAL` | По алфавиту | По `title` |
| `BY_PROJECT` | По проектам | Группировка по **имени** проекта (резолв `projectId` → `name`), внутри — по важности, затем по названию. Задачи без проекта уходят в конец по sentinel-символу `"￿"` |
| `DURATION` | По времени | По возрастанию `duration` |

Стартовый режим зависит от `feat_smart_sort`: включена — `PRIORITY`,
выключена — `ALPHABETICAL` (`TaskViewModel.defaultSortMode()`).

Архив сортируется отдельно и всегда по убыванию `completed` — спиннера там нет.

### Фильтры категорий

Sentinel-значения позволяют различить «все» и «без категории»:

| Значение | Константа | Смысл |
|---|---|---|
| `null` или `""` | `FILTER_ANY` | Фильтр не применяется |
| `"__none__"` | `FILTER_NONE` | Только задачи с `null` в этом поле |
| Конкретный UUID | — | Только задачи с этим id |

`applyCategoryFilters()` применяет три фильтра конъюнктивно. На вкладке «Стек»
доступны спиннеры локации и типа (фильтра по проекту в UI нет — проект фильтруется
через экран «Папки»).

### Поиск

Только на вкладке «Стек», без учёта регистра, по двум полям — `title` и `purpose`.
Реализован фильтрацией уже загруженного списка в памяти, SQL-запроса нет.

### Порядок операций при построении списка

```
allTasks (LiveData, все задачи)
   → фильтр по статусу (либо merged: Стек + Сегодня)
   → applySortMode(...)
   → applyCategoryFilters(...)
   → фильтр по строке поиска
   → adapter.submitList(...)
```

## 9. Экраны и функционал

### 9.1 OnboardingActivity — первичная настройка

Семь шагов в `ViewFlipper`, два из них условные.

| № | Шаг | Что настраивается |
|---|---|---|
| 0 | Приветствие | — |
| 1 | Системное | Тема (светлая / тёмная / системная), включение и время утреннего уведомления |
| 2 | Возможности | `feat_split_today`, `feat_calendar`, `feat_projects`, `feat_locations`, `feat_task_types`, `feat_smart_sort`, `feat_defer` |
| 3 | Коэффициенты | Четыре слайдера весов + блок перегрузки (`feat_overload`, порог, бонус). **Пропускается**, если `feat_smart_sort` выключен |
| 4 | Календарь | Режим `range` / `point` |
| 5 | Уровень помощи | `minimal` / `standard` / `advanced` / `custom` |
| 6 | Поля задачи | Видимость полей + чекбоксы обязательности. **Пропускается**, если уровень не `custom` |

Особенности реализации:

- `computeNext()` вычисляет следующий видимый шаг, пропуская отключённые; счётчик
  «шаг N из M» пересчитывает M динамически.
- Выбор темы вызывает `recreate()` активности. Текущий шаг сохраняется в
  `onSaveInstanceState` под ключом `onb_current_step` — без этого пользователя
  отбрасывало на первый экран.
- Кнопка «Пропустить» видна **только при переустановке** с восстановленными
  настройками (`EXTRA_ALLOW_SKIP`). При чистой установке онбординг обязателен.
- `finishOnboarding()` пишет флаг через `commit()`, а не `apply()`: синхронная
  запись гарантирует, что настройки попадут в файл до того, как Android запустит
  Auto Backup.

### 9.2 MainActivity — каркас

Нижняя навигация из пяти слотов, центральный — пустой placeholder, под которым
живёт FAB создания задачи:

```
[ Сегодня ] [ Стек ] [ (+) ] [ Календарь ] [ Настройки ]
```

- Вкладки «Сегодня» и «Календарь» скрываются по feature-флагам. При скрытом
  «Сегодня» вкладка «Стек» переименовывается в «Задачи» и работает в объединённом
  режиме (`StackFragment.newMerged()`).
- `alignFabToCenterSlot()` сдвигает FAB через `translationX`: при скрытых вкладках
  `BottomNavigationView` перекладывает только видимые пункты, и геометрический
  центр панели перестаёт совпадать с пустым слотом.
- FAB виден на всех вкладках, включая «Настройки», и прячется только внутри
  модальных экранов.
- Кнопка пожертвования в верхней панели открывает `https://pay.cloudtips.ru/p/e0ddf2ed`.
- При старте: запрос `POST_NOTIFICATIONS` (Android 13+), `scheduleDaily()`,
  `vm.promoteDueDeferred()` (догоняем пропущенные переносы), `scheduleDeferPromotion()`.

Логика первого запуска подробно разобрана в §12.

### 9.3 TodayFragment — план дня

- Список задач со статусом «Сегодня», спиннер сортировки.
- **Hero-блок нагрузки**: суммарные минуты, число задач, прогресс-бар с отметками
  половины порога и самого порога, текстовый статус и перекраска прогресса
  (`load_ok` / `load_warn` / `load_over`).
- Действия на карточке: «Выполнить» (→ Архив, проставляется `completed`) и
  «В стек» (→ Стек).

### 9.4 StackFragment — бэклог

Работает в двух режимах.

**Раздельный** (`feat_split_today = true`): показывает только статус «Стек».
Действия: «В сегодня», «Удалить» (с диалогом подтверждения) и — при включённом
`feat_defer` — третья кнопка «Отложить».

**Объединённый** (`newMerged()`): один список из «Стек» + «Сегодня», единственное
действие «Выполнить». Колонка нагрузки и разделитель в шапке скрываются.

Дополнительно: поле поиска, спиннеры фильтров локации и типа, счётчик задач
с русской плюрализацией, светофор нагрузки дня.

**Отложенное планирование.** Кнопка открывает `MaterialDatePicker`, ограниченный
датами строго после сегодня. Пикер оперирует UTC-миллисекундами, поэтому
конвертация идёт через `ZoneOffset.UTC` — иначе выбранный день «уезжал» бы на
сутки в зависимости от часового пояса. Отложенная задача получает фиолетовую
обводку карточки и дату на кнопке («До 5 июн»). Ручной перенос в «Сегодня»
автоматически снимает отложенность.

### 9.5 CalendarFragment — месячная сетка

Кастомная сетка 7 колонок (`GridLayoutManager` + `MonthCalendarAdapter` +
`CalendarCellView`), с добором дней предыдущего и следующего месяца до полных недель.
Неделя начинается с понедельника.

**Два режима отображения дедлайнов** (`calendar_mode`):

- **`range`** (по умолчанию) — задача видна в каждый день отрезка
  `[deadlineStart, deadline]`. Если `deadlineStart` пуст, началом считается дата
  создания задачи.
- **`point`** — задача видна только в день `deadline`.

Переключение мгновенное, без перезапуска.

**Ячейка-«пончик».** Каждая ячейка — кольцо, разделённое на равные секторы по числу
задач дня. Радиус сектора кодирует длительность задачи по экспоненциальной кривой
с насыщением:

```
radiusRatio = 0.52 + (1 − e^(−duration / 60)) · 0.48
```

Кривая самоограничена: сколь угодно длинная задача асимптотически приближается к
максимуму, но не превышает его; короткие задачи не схлопываются в точку благодаря
полу 0.52. Отрисовка идёт в два прохода — сначала все заливки, затем все обводки,
чтобы заливка следующего сектора не перекрывала обводку предыдущего. В центре —
белый «хаб» (13 % радиуса), чтобы номер дня оставался читаемым.

Цвет сектора по приоритету правил:

| Условие | Цвет |
|---|---|
| Отложенная задача в день откладывания | фиолетовый `#8842B3` |
| Статус «Сегодня» | голубой `#7FB5EC` |
| Важность «Высокая» | красный `#F25757` |
| Важность «Средняя» | жёлтый `#FDFF73` |
| Важность «Низкая» | зелёный `#85EF82` |

Под сеткой — список задач выбранного дня. Тап по названию месяца возвращает к
текущему месяцу и выбирает сегодня. Русская локаль для названий месяцев и дат
зашита константой `Locale("ru")`, чтобы системная локаль устройства не ломала
формат.

### 9.6 SettingsFragment — настройки

Дублирует весь онбординг и добавляет то, чего там нет:

- **Тема** — переключатель light/dark/system, применяется мгновенно.
- **Возможности** — 7 тумблеров. Строка «Отложенное планирование» затемняется
  (alpha 0.4) и блокируется при выключенном разделении «Сегодня»/«Стек».
- **Режим календаря** — range/point.
- **Уровень помощи** + кнопка настройки custom-уровня (диалог с 8 чекбоксами;
  недоступные поля показаны с alpha 0.38 и принудительно сбрасываются в `false`).
- **Поля задачи** — 5 тумблеров видимости.
- **Уведомления** — включение и выбор времени, с немедленным перепланированием.
- **Коэффициенты алгоритма** — 4 слайдера + порог перегрузки + бонус, кнопки сброса
  к дефолтам и **явная кнопка «Сохранить»** (в отличие от остальных настроек, которые
  пишутся мгновенно).
- **Папки** — карточка-кнопка, открывающая `FoldersFragment` модально. Скрыта, если
  выключены все три вида категорий.
- **Архив** — кнопка, открывающая `ArchiveFragment` модально.
- **Контакты** — почта `supportkotatask@gmail.com` и две ссылки на Telegram.

> Тумблера `feat_overload` в настройках **нет** — его можно включить/выключить
> только в онбординге (шаг 3).

### 9.7 FoldersFragment — папки категорий

Три секции (Проекты / Локации / Типы), каждая скрывается своим feature-флагом.
В каждой строке — название и счётчик **активных** задач (Стек + Сегодня, без архива).
Внизу каждой секции — системная папка «Без …» с `id = null`, которую нельзя удалить.
Кнопки добавления открывают общий диалог ввода названия; удаление —
с подтверждением и автоматическим отвязыванием задач.

### 9.8 CategoryTasksFragment — задачи одной категории

Открывается тапом по папке. Показывает активные задачи, отфильтрованные по одной
оси. Внутри папки проекта метка проекта на карточках скрыта как избыточная.
Есть кнопка добавления задачи с предзаполненной категорией
(`AddTaskFragment.forCategory()`).

### 9.9 AddTaskFragment — создание и редактирование

Один фрагмент в двух режимах, различаемых фабричными методами:
`forEdit(taskId)` и `forCategory(kind, id)`.

Поля: название, начало дедлайна, дедлайн, важность (три «пилюли»), длительность,
цель, три строки категоризации с диалогом выбора.

Особенности:

- **Видимость полей** пересчитывается до навешивания слушателей, чтобы не вешать
  их на скрытые строки. Заголовок «Категоризация» скрывается, если все три строки
  ушли в `GONE`.
- **Quick-add**: в диалоге выбора категории есть пункт «Добавить новый…», который
  создаёт сущность и сразу выбирает её для текущей задачи через callback
  `onCreated`.
- **Защита edit-режима от гонки**: если `LiveData` ещё не загрузилась, задача по id
  не находится. Вместо сброса `editingTaskId` в `null` (что превратило бы
  редактирование в создание новой задачи) выставляется флаг `awaitingPrefill`, и
  фрагмент подписывается на первое обновление `allTasks`.
- **Date picker** при редактировании разрешает прошедшие даты, при создании — нет.
- После создания задачи из FAB происходит переход на вкладку «Стек»; при создании
  из папки или при редактировании модальный экран просто закрывается.

**Валидация по уровню помощи:**

| Поле | minimal | standard | advanced | custom |
|---|---|---|---|---|
| Название | обяз. | обяз. | обяз. | обяз. |
| Дедлайн | — | обяз. | обяз. | по чекбоксу |
| Длительность | — | — | обяз. | по чекбоксу |
| Цель | — | — | обяз. | по чекбоксу |
| Начало дедлайна | — | — | — | по чекбоксу |
| Проект / Локация / Тип | — | — | — | по чекбоксу |

Длительность дополнительно проверяется на диапазон **1…600 минут** независимо от
уровня. Пустое поле при необязательности даёт дефолт 30. Ограничение введено
потому, что `0` ломал расчёт приоритета, а мусорные значения вроде `999999`
искажали график дневной нагрузки.

Требование обязательности применяется только к **видимым** полям: скрытое поле
не может заблокировать сохранение.

### 9.10 ArchiveFragment — архив

Список выполненных задач, отсортированный по убыванию времени выполнения.
Режим множественного выделения с чекбоксами, массовое удаление выбранных и
«удалить всё» — оба с диалогом подтверждения и точным числом задач в тексте.
На карточке показывается таймстамп выполнения в формате `dd MMM yyyy, HH:mm`.

### 9.11 Карточка задачи (TaskAdapter)

Единый адаптер на все списки, поведение переключается через `enum TabMode`:
`TODAY`, `STACK`, `ARCHIVE`, `CALENDAR`, `MERGED`.

Элементы карточки: цветная полоса важности слева, название, точка и подпись
важности, чип дедлайна (с датой или диапазоном `start → end`), чип длительности,
бейдж скора (во всех режимах кроме архива), строка локации, строка проекта,
таймстамп выполнения (только архив).

Чип дедлайна меняет и текст, и цвет: «Просрочено · 3 июн» (красный), «Сегодня»
(жёлтый), «5 июн» (нейтральный).

Обводка карточки кодирует состояние по приоритету правил: архив → нейтральная;
отложенная в стеке → фиолетовая; в календаре со статусом «Сегодня» → акцентная;
дедлайн сегодня → жёлтая; иначе нейтральная.

Набор кнопок зависит от режима:

| Режим | Кнопка 1 | Кнопка 2 | Кнопка 3 |
|---|---|---|---|
| `TODAY` | Выполнить | В стек | — |
| `STACK` | В сегодня | Удалить | Отложить (если включено) |
| `MERGED` | Выполнить (на всю ширину) | — | — |
| `CALENDAR` | Выполнить / В сегодня (по статусу) | В стек / Удалить | — |
| `ARCHIVE` | — (вместо кнопок — чекбокс выделения) | — | — |

### Как настройки применяются

| Способ | Где используется |
|---|---|
| Мгновенно, `apply()` | Тема, режим календаря, feature-флаги, видимость полей, уровень помощи |
| Мгновенно + `applyFeatureFlagsToNav()` | Флаги, влияющие на нижнюю навигацию |
| По кнопке «Сохранить» | Коэффициенты алгоритма, порог перегрузки, бонус |
| Синхронно, `commit()` | Завершение онбординга; восстановление настроек из бэкапа |

Реактивности у настроек нет: уже открытый экран не перечитает изменившийся флаг
сам. Например, `assistanceLevel` в `AddTaskFragment` фиксируется на время жизни
фрагмента, и новое значение применится только к следующему открытию формы.

## 11. Фоновые процессы

Два `CoroutineWorker`, оба построены по схеме **самоперепланирующегося
`OneTimeWorkRequest`**, а не `PeriodicWorkRequest`. Причина: периодический воркер
не гарантирует попадания в конкретное `HH:MM` — Android группирует задачи в окна.
Одноразовый запрос с точно вычисленной задержкой ставится заново после каждого
срабатывания.

```kotlin
fun calculateInitialDelayMs(targetHour: Int, targetMinute: Int = 0,
                            now: Long = System.currentTimeMillis()): Long {
    val target = Calendar.getInstance().apply {
        timeInMillis = now
        set(Calendar.HOUR_OF_DAY, targetHour); set(Calendar.MINUTE, targetMinute)
        set(Calendar.SECOND, 0); set(Calendar.MILLISECOND, 0)
        if (timeInMillis <= now) add(Calendar.DAY_OF_MONTH, 1)   // время уже прошло → завтра
    }
    return target.timeInMillis - now
}
```

### NotificationWorker — утренний дайджест

- Тег уникальной работы: `daily_notif`, политика `ExistingWorkPolicy.REPLACE`.
- Срабатывает в заданное пользователем время, показывает список задач со статусом
  «Сегодня»: первые 5 строк плюс «ещё N».
- Перед показом повторно проверяет `notif_enabled` — пользователь мог выключить
  уведомления, пока воркер ждал.
- Канал `mark_daily`, `IMPORTANCE_DEFAULT`, `VISIBILITY_PRIVATE`. На экране
  блокировки через `setPublicVersion()` показывается урезанная версия без списка
  задач — названия задач не утекают на locked screen.
- После показа вызывает `reschedule()` на то же время завтра.

### DeferPromoteWorker — перенос отложенных задач

- Тег: `defer_promote`, срабатывает в 00:00.
- Выполняет один SQL-запрос `promoteDueDeferred(today)` и перепланирует себя.
- Исключения **намеренно проглатываются** без retry: перенос не критичен, а
  retry-шторм WorkManager хуже пропущенного дня. Страховка — catch-up при запуске
  приложения: `MainActivity.onCreate()` вызывает `vm.promoteDueDeferred()`.

### BootReceiver

Слушает `ACTION_BOOT_COMPLETED` и перепланирует **оба** воркера — после
перезагрузки очередь WorkManager для отложенных одноразовых задач не восстанавливается
автоматически в нужное время.

## 12. Резервное копирование и восстановление

В приложении **два независимых механизма** бэкапа, работающих совместно.

### Механизм 1: Android Auto Backup (система)

Настроен в `backup_rules.xml` (API 23–30) и `data_extraction_rules.xml` (API 31+).
Бэкапятся `mark_prefs.xml` и файл базы `mark_db`; WAL/SHM/journal явно исключены
(при `JournalMode.TRUNCATE` они не создаются, исключения оставлены для совместимости
при обновлении со старых версий).

Слабое место: Auto Backup запускается максимум раз в сутки и только при зарядке +
Wi-Fi + простое устройства. Изменения между двумя бэкапами теряются.

### Механизм 2: локальный JSON-снимок (BackupExportManager)

Компенсирует слабость первого.

- **Когда пишется.** `KotaTaskApp` регистрирует `ActivityLifecycleCallbacks` и
  считает запущенные активности. Когда счётчик падает до нуля (приложение ушло в
  фон), в IO-корутине пишется снимок.
- **Куда.** `Downloads/kotatask_backup.json` через `MediaStore` — **каталог не
  очищается при удалении приложения**, поэтому файл переживает переустановку.
- **Что.** Формат версии 2: все ключи `mark_prefs`, разложенные по типам
  (`floats` / `ints` / `booleans` / `strings`), и полный массив задач.
  Категории (проекты, локации, типы) в снимок **не входят** — см. §15.
- **Ограничение.** Работает только на API 29+. На Android 8–9 приложение полностью
  полагается на Auto Backup.

### Логика первого запуска

Ключевой приём — флаг `install_initialized` в `mark_local`, который **не бэкапится**.
Это позволяет отличить три сценария:

| `install_initialized` | `onboarding_done` | Вывод | Действие |
|---|---|---|---|
| нет | `false` | Чистая установка | Онбординг без кнопки «Пропустить» |
| нет | `true` | Переустановка: настройки пришли из бэкапа | Онбординг **с** кнопкой «Пропустить» |
| есть | `true` | Обычный запуск | Сразу главный экран |

При первом запуске на данной установке приложение:

1. Ставит `install_initialized = true`.
2. Синхронно читает `Downloads/kotatask_backup.json` (файл маленький, < 5 мс).
3. **Настройки** восстанавливает всегда через `commit()` — локальный снимок
   свежее Auto Backup. Ключ `onboarding_done` при этом пропускается: им управляет
   только `OnboardingActivity`.
4. **Задачи** восстанавливает из JSON **только если БД пуста** — то есть если
   Auto Backup не отработал. Room-база считается более авторитетным источником.

## 13. Сборка и релиз

### Конфигурация

```gradle
buildTypes {
    release {
        if (hasReleaseSigning) { signingConfig signingConfigs.release }
        minifyEnabled false
        proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
    }
}
```

**Подпись релиза** читается из Gradle-свойств или переменных окружения и включается
только если заданы все четыре значения:

| Свойство / переменная |
|---|
| `RELEASE_STORE_FILE` |
| `RELEASE_STORE_PASSWORD` |
| `RELEASE_KEY_ALIAS` |
| `RELEASE_KEY_PASSWORD` |

Если хотя бы одно не задано, `signingConfig` не применяется и релизная сборка
остаётся неподписанной. Ключи в репозитории не хранятся (`*.jks`, `*.keystore`
в `.gitignore`).

**Минификация выключена** (`minifyEnabled false`). Подключение `proguard-rules.pro`
присутствует, но без `minifyEnabled true` не применяется — правила лежат мёртвым
грузом.

### Автокопирование APK

Блок `afterEvaluate` в `app/build.gradle` после каждой сборки копирует APK в
`Code/Builds/` под именем `KotaTask_${yyyyMMdd_HHmm}.apk`.

Путь вычисляется как `rootProject.projectDir.parentFile.parentFile/Builds` —
то есть жёстко завязан на структуру каталогов репозитория. При переносе модуля
на другую глубину вложенности APK будет копироваться не туда.

В архиве встречаются также имена вида `KotaTask-v4.8-backup-persist-skip-debug.apk` —
это ручная конвенция версионирования, которая с автогенерируемым именем по
таймстампу не совпадает.

### Вспомогательный скрипт

`Code/KotaTask-main/seed_tasks.sh` — создаёт SQLite-файл с точной схемой Room на
хосте, вставляет 4 тестовые задачи и заливает базу на устройство через
`/data/local/tmp` + `run-as cp`. Не зависит от состояния приложения.
Требует `adb` и `sqlite3` на хосте.

> Скрипт содержит **зашитую копию схемы Room**. При любом изменении схемы его
> нужно обновлять вручную, иначе он зальёт базу, несовместимую с текущей версией.

### Тесты

Автотестов нет: каталоги `app/src/test/` и `app/src/androidTest/` отсутствуют.
Покрытие — 0 %.

### Противоречия и ловушки

**Два набора дефолтных весов.** `data class Coefficients` объявляет
`0.50 / 0.30 / 0.15 / 0.05`, а `TaskViewModel.getCoefficients()` читает из prefs с
дефолтами `0.45 / 0.35 / 0.10 / 0.10`. Работают вторые — первые недостижимы,
поскольку VM всегда конструирует объект явно. Читающий код легко ошибётся.
Дефолты продублированы ещё и третий раз, как целые проценты, в приватных константах
`SettingsFragment` (45/35/10/10) и в литералах `OnboardingActivity`.

**Категории не попадают в локальный бэкап.** `BackupExportManager` сохраняет
задачи вместе с `projectId` / `locationId` / `taskTypeId`, но **не сохраняет сами
таблицы** `projects`, `locations`, `task_types`. Если восстановление пойдёт по
локальному пути (Room-база пуста, задачи берутся из JSON), задачи получат ссылки на
несуществующие категории: в UI это выглядит как пустые метки, а в папках такие
задачи не находятся. Auto Backup эту проблему не имеет, поскольку копирует базу
целиком.

**Светофор нагрузки игнорирует `feat_overload`.** `applySortMode()` при выключенном
флаге подставляет «бесконечный» порог, а `TodayFragment` и `StackFragment` читают
`vm.getOverloadLimitMinutes()` напрямую и продолжают рисовать шкалу и цвета.

**`feat_overload` недоступен в настройках.** Включить его обратно после выключения
можно только повторным прохождением онбординга.

**Сумма весов не нормализуется.** Пользователь может выставить все четыре слайдера
в ноль — тогда все задачи получат скор 0.00 и сортировка «по приоритету» станет
произвольной (устойчивой, но бессмысленной).

**Полная перезагрузка списка на каждое изменение.** Любая правка одной задачи
триггерит `LiveData` со всем списком, после чего каждый активный фрагмент заново
фильтрует и сортирует всё в памяти. При сотнях задач и режиме календаря `range`
(который разворачивает каждую задачу на все дни диапазона) это станет заметно.

**`notifyDataSetChanged()` в календаре.** `MonthCalendarAdapter.update()` и
`updateTasks()` перерисовывают всю сетку целиком, без `DiffUtil`.

**Отсутствие внешних ключей.** Целостность держится на дисциплине вызова
`unlinkFromTasks()` в репозиториях. Любой обходной путь оставит осиротевшие ссылки.

**`versionCode` не растёт.** Остаётся `1` при `versionName "1.0-beta"`, хотя
локальный архив сборок дошёл до v4.8. Для публикации в Google Play это блокер.

**Название пакета.** `com.mark.app` и `rootProject.name = "Mark"` не соответствуют
продукту. Переименование `applicationId` для уже установленных сборок означает
новое приложение — данные пользователей не перенесутся автоматически.

**Ноль тестов** при наличии чистой, тестируемой логики: `PriorityCalculator` —
чистые функции без зависимостей от Android, `calculateInitialDelayMs()` принимает
`now` параметром специально ради тестируемости, но тестов на них нет.
